# v0.4 Productization Course

Status: productization course for the `v0.4.0` milestone.
Source: PM skill pass over the v0.4 north star, latest `master`, and the live
milestone state on 2026-06-10. Tracking issue: #1046.

## Decision

The product is the **independent proof engine built on your own Claude history**.
The dashboard is the data layer that makes the proof possible.

Do not productize v0.4 as a broader analytics dashboard, a generic org
observability tool, or a nicer cost report. Those layers are useful, but the
business exists only if the product can close the loop:

1. detect a high-evidence workflow problem in real Claude history,
2. choose a specific recommendation,
3. pre-register a controlled experiment,
4. run matched fixture pairs with objective gates,
5. publish a receipt with effect size, uncertainty, dollars, rollout guidance,
   and model-version freshness.

The receipt may prove the recommendation, refute it, or produce a scientific
null. Any of those is a product outcome if it is externally reviewable and
honest.

## Beachhead

First segment: Claude Code power users and hands-on AI engineering leads on
small teams.

They are close enough to the work to care about session-level forensics, but
responsible enough for spend and team practice to care about proof. This keeps
the first buyer/user narrow:

- heavy Claude Code usage,
- visible cost or reliability pain,
- appetite for local-first tools,
- ability to change team instructions, skills, hooks, or workflow norms,
- willingness to believe a receipt more than a model-written summary.

Do not start with broad enterprise buyers. Enterprise bootstrap auth is useful
packaging infrastructure, but org dashboards, leaderboards, procurement, SSO,
and multi-seat aggregation pull the product toward first-party analytics and
OTel competitors. The v0.4 story is "solo proof, team framing": one developer's
receipt should make the manager/team rollout legible.

## Value Proposition

For teams adopting Claude Code heavily, the current alternatives are weak:

- first-party analytics show aggregate usage, not session-level causes,
- cost CLIs show spend, not what to change,
- local dashboards show what happened, not whether a fix worked,
- LLM-generated advice is cheap to produce and hard to believe.

This product turns local Claude history into proof-backed workflow changes.
Before: "we think context waste is expensive." After: "this repo-map treatment
reduced the relevant token distribution by E, CI [a,b], on N matched fixture
pairs, with quality gates passing; here is the dollar projection and the model
version it is valid for."

## Metrics

Business game: Productivity. The product helps people complete engineering work
more efficiently and more reliably with coding agents.

Product North Star after v0.4:

> Current proof-backed workflow changes adopted per active workspace-month.

This is customer-centric because it measures changes a user can actually trust
and apply. It is not revenue, raw usage, chart views, or total recommendations.

v0.4 OMTM:

> One externally reviewed proof receipt from a pre-registered workflow
> experiment, or an honest null/not-yet-provable verdict.

Input metrics:

- eligible high-evidence recommendations with Class A / Class B split,
- pre-registrations committed before batch execution,
- matched fixture pairs completed under objective gates,
- receipts with effect size, uncertainty, dollars, and external review refs,
- receipt freshness state: current, stale, or revoked after model changes,
- adopted recommendations whose receipts remain current.

## Critical Path

The implementation order should stay receipt-first:

1. **#975 shared substrate** - committed eval result schema and curated fixture
   corpus. This is the common contract for model-routing evals and the workflow
   proof.
2. **#594 / #598 replay honesty** - objective-first verdict path so the proof
   does not depend on an aesthetic LLM judge.
3. **#579 recs efficacy surface** - show gated matched-pair efficacy through
   the existing detector path, including price deltas from v0.3 accounting.
4. **#995 release gate** - produce the externally reviewed proof receipt, null
   receipt, or explicit not-yet-provable verdict.
5. **#996 positioning** - update README and landing copy only to the level the
   receipt supports. Method claims are allowed before proof; result claims wait
   for the actual receipt.

Supporting context:

- #573 remains the parent for measurable recs impact.
- #582 and #583 are closed enabling work for injected/withheld recs and replay
  eligibility.
- #1043 is closed and defines the epistemic boundary: distributional claims
  only, model-version scoped, no per-run guarantees.

## Packaging

Keep the free/local surface valuable: live local analytics, the public sample,
cost/context views, and recommendation discovery. That surface earns trust and
feeds the proof engine.

The paid or server-side value should be proof automation and upkeep:

- pre-registration workflow,
- fixture corpus management,
- batch execution and objective gates,
- proof receipt generation,
- external-review packet,
- receipt revalidation when model versions change,
- enterprise auth/audit only as packaging for controlled deployment.

Do not make "team dashboard" the first paid thesis. The paid thesis is recurring
proof and revalidation.

## Non-Goals

Explicitly out of scope for this course:

- generic LLM observability,
- org leaderboards and broad aggregate analytics,
- broad multi-tenant SaaS before the proof loop works locally,
- shareable dashboards as a growth loop,
- non-Claude generalization before the first proof,
- shadow-testing-agent language that misnames experiments on developers using
  the agent,
- model-narrated proof without pre-registration, objective gates, and external
  review.

## Operating Rule

When choosing between two v0.4 tasks, prefer the one that increases the chance
of a credible receipt. If a task improves the dashboard but does not help a
specific proof receipt exist, stay fresh, or become believable, it is secondary
for this milestone.
