# Ingest throughput baseline (#665)

Measured 2026-06-05 against the reproducible sample corpus generated by
`scripts/sample-data/build-corpus.mjs` (18 sessions, 231 KB of transcript
JSONL). Run with:

```
npm run bench:ingest
# or:
node --import ./scripts/register-ts.mjs scripts/ingest-bench.mjs
```

Platform: Node 24 / Linux 5.15 (WSL2), tmpfs fixture, no container.

---

## Parse hot paths (per-parser micro-benchmarks, median of 7 runs)

| Parser | Corpus | Median |
|---|---|---|
| `parseSessionJsonl` (parse-sessions.ts) | 18 sessions | 1.4 ms |
| `parseToolUsage` (parse-tools.ts) | 18 sessions | 1.1 ms |
| `parseSessionTimeline` (parse-timeline.ts) | 18 sessions | 1.4 ms |

**Target:** keep each parser under 3x baseline (< 4 ms for 18 sessions) on the
sample corpus. Growth beyond that indicates a regression in the parse loop.

---

## `assembleDataset()` end-to-end

| Path | Time |
|---|---|
| Cold (artifact cache empty, first call) | 10.5 ms |
| Warm (artifact cache hot, median of 7) | 2.0 ms |
| Warm min / max | 1.7 ms / 2.9 ms |

**Target:** warm `assembleDataset()` under 6 ms on the sample corpus (3x
baseline). Cold (first-call or post-invalidation) under 30 ms.

Note: the live `~/.claude` corpus in `baseline.md` (100 sessions, 82 MB) shows
19.6 s — but that baseline predates the #624 artifact-cache and dataset-cache
seams. Those caches now make the hot path (unchanged corpus) identical to the
warm path above. The 19.6 s figure was dominated by brotli-11 compression on
every request, which is now also cached.

## Artifact-dir walk quantification

Issue #539 added parsers that walk top-level `~/.claude` directories. Issue
#665 was filed to quantify the "~9 uncached artifact-dir walks."

### Exact walk count per `assembleDataset()` call

`assembleDataset()` calls `cachedArtifact()` for each of these 11 paths:

| # | Key | Path |
|---|---|---|
| 1 | `tasks` | `~/.claude/tasks/` |
| 2 | `teams` | `~/.claude/teams/` |
| 3 | `session-registry` | `~/.claude/sessions/` |
| 4 | `telemetry` | `~/.claude/telemetry/` |
| 5 | `debug` | `~/.claude/debug/` |
| 6 | `file-history` | `~/.claude/file-history/` |
| 7 | `plans` | `~/.claude/plans/` |
| 8 | `backups` | `~/.claude/backups/` |
| 9 | `insights-meta` | `~/.claude/usage-data/session-meta/` |
| 10 | `insights-facets` | `~/.claude/usage-data/facets/` |
| 11 | `insights-report` | `~/.claude/usage-data/report.html` |

Total: **11 artifact paths per `assembleDataset()` call** (not 9 — the
issue said "~9"; the actual count is 11 including the two insights subdirs and
the report file). Confirmed at runtime: cold `assembleDataset()` triggers
exactly 11 parser calls (`_getArtifactParseCount() == 11`); warm call triggers
0 (all cache hits).

`ingest()` additionally runs 5 `hashTree()` walks for the content fingerprint
(usage-data, skills, agents, commands, plugins/cache) — these are in the ingest
path, not `assembleDataset()`.

### Artifact section wall-clock share

| Path | assembleArtifacts() | share of assembleDataset |
|---|---|---|
| Cold (all 11 parsed from disk) | 2.5 ms | 24% of 10.5 ms |
| Warm (all 11 served from cache) | 0.4 ms | 18% of 2.0 ms |

On the warm path the artifact section is ~18% of total `assembleDataset()`.
The remaining ~82% is the session-blob read-back (SQLite JSON.parse loop) and
the history.jsonl union. The artifact walks are not the dominant cost on a warm
cache.

### Caching status

The #624 artifact-ingest cache landed before this benchmark was written. Each
`cachedArtifact()` call runs `artifactSignature()` (a cheap stat-only tree
walk — no file bytes read) to check for changes, then either:
- **HIT**: returns the stored JSON from SQLite — no parser runs, no file reads.
- **MISS**: runs the full parser, stores the result, returns the fresh value.

On the sample corpus with an unchanged tree, all 11 are HITs on the second call.
The uncached stat-only signature walk (one `readdirSync` per dir, no file
content read) is what remains on the warm path — that is the residual cost
#624 left for #624's follow-up (per-dir stat caching is out of scope for #665).

## Cold ingest worker prototype (#855)

Take a measurement with:

```
CHD_COLD_INGEST_TARGET_MB=128 \
CHD_COLD_INGEST_WORKERS=8 \
node --import ./scripts/register-ts.mjs scripts/cold-ingest-bench.mjs --measure-only
```

`--measure-only` is the supported way to report timings without gating. Do NOT
reach for a threshold value that cannot be failed: the older recipe here passed
`CHD_COLD_INGEST_MIN_SPEEDUP=0`, which "worked" only because a comparison
against a non-positive threshold is always false — the same accident that let a
real regression exit green (#3076). The threshold is now fail-closed and rejects
zero, so drop the variable and pass the flag.

The benchmark scales the deterministic sample corpus into a first-ever
empty-cache corpus on disk, parses session rows serially and through a bounded
worker pool, then asserts byte-equivalent `session_blob` rows and
transcript-derived dataset slices before reporting timing.

Measured 2026-07-29 (`72b62944` + #3076), 8 workers, Node 24.15 with a 2240 MB
heap limit:

| Path | Corpus | Time |
|---|---:|---:|
| Serial read + parse | 10,043 sessions / 128.0 MiB | 14,507.2 ms |
| Worker read + parse | 8 workers / same corpus | 4,083.8 ms |

Speedup: **3.55x**. The benchmark asserts byte-identical session rows before
printing timing. Transcript-derived dataset hash:
`fa58a9a82c1693dab6fab64c5ad1a58973e7d0b1`.

Two notes on why this supersedes the 2026-06-11 entry (30,504 sessions /
384.0 MiB, 14,929.7 ms serial vs 5,616.5 ms worker, 2.66x, dataset hash
`1b8be9afe0738bc1a08c9feee26531478f131125`) rather than sitting beside it:

- **The old dataset hash is not reproducible and should not be compared
  against.** `assembleTranscriptDataset` kept a hand-written copy of the
  dataset-key list; ingest later gained the `valueFlow` and `secretsAtRest`
  signals, and every run after that died on a `TypeError` before reporting.
  The accumulator is now derived from `SESSION_SIGNALS`, so the hash covers
  the current signal set — a different, larger dataset than the June figure.
- **The 384 MiB corpus is a separate, still-open problem.** Both the serial and
  the worker row sets are held in memory at once and then JSON-serialized twice
  for the equivalence check, so peak heap scales with the corpus. At 384 MiB
  that exceeds a 2240 MB heap limit and the process dies with
  `FATAL ERROR: Reached heap limit`. This reproduces identically on `72b62944`
  without any of the #3076 changes, so it is pre-existing rather than a
  regression; it is filed separately. Until it is bounded, 128 MiB is the
  largest corpus that completes on a default-heap host.

The prototype keeps SQLite out of workers. Workers return parsed row payloads
only; the parent process owns the deterministic session-id merge order and is
the only future SQLite writer.
