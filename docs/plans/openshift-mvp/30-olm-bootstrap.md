# 30 — OLM Bundle + Prereq Bootstrap (blocker #3)

> **Status:** reconciled to ADR 0011 (single-tenant #1247 substrate, Probaitio naming). The
> multi-tenant/zero-knowledge pieces (Keycloak, client-side encryption, encrypted-blob store,
> public write gate, compute proxy) are **deferred to #467** and collected in a section below.
>
> **Superseded by what shipped (as of 2026-07-22):** OLM was **bypassed** — the MVP substrate
> shipped (#1559) without an OLM bundle/bootstrap. Treat the OLM-bundle packaging below as a
> point-in-time proposal, not current architecture.

> Area owner doc for the #1247 single-tenant Probaitio substrate.
> Scope: how the `probaitio-operator` (operator-sdk **hybrid.helm** plugin: one Helm chart
> for the app + a thin Go reconciler for dependency CRs) is **packaged as an OLM bundle**,
> indexed into a **File-Based Catalog (FBC)**, surfaced via a **custom CatalogSource**, and —
> the actual fix — **bootstrapped behind its required-CRD operators in the right order** so the
> Probaitio `InstallPlan` does not fail admission.
>
> Companion docs (same dir): `10-*` reconciler/CR design, `20-*` server auth/S3/zero-knowledge,
> `40-*` Vault seeding. This doc is authoritative for everything OLM + install ordering.

## TL;DR decisions (decisive; do not re-litigate)

1. **Use OLM *Classic* (v0), not OLM v1 / `ClusterExtension`, for the MVP.** OLM v1 *cannot
   authenticate a private-registry catalog* (upstream **OCPBUGS-36364**: "OLM v1 currently
   cannot authenticate private registries"). Our catalog + bundle + operator images live in a
   private Quay org, so v1 is a non-starter until that gap closes. Classic's `CatalogSource`
   has a first-class `spec.secrets` field for exactly this. We revisit v1 post-MVP.
2. **Bundle declares `requiredCRDs` (via `olm.gvk.required` properties)** for the external
   APIs the reconciler creates instances of. For the single-tenant MVP the required set is:
   `VaultStaticSecret` (VSO). If a blob-substrate operator (e.g. ODF/NooBaa-OBC) is used,
   `ObjectBucketClaim` is also required. Because OLM resolves these at `InstallPlan` admission,
   the Probaitio subscription **fails admission if those CRDs are absent**. That is the blocker.
   The fix is an **ordered bootstrap** that installs + waits-Ready for VSO (and optionally the
   blob-substrate operator) *before* creating the Probaitio `CatalogSource`/`Subscription`.
   Keycloak/RHBK is **not** an MVP prereq — it is deferred to #467 (see below).
3. **`installPlanApproval: Manual`** on the Probaitio `Subscription` for the MVP — the
   InstallPlan is inspected and approved by the runbook (or the bootstrap Job), never silently
   auto-upgraded.
4. **The Helm chart still owns only always-present app resources** (Deployment/Service/Route/PVC/
   `envFrom`). Every external-dependency CR (`ObjectBucketClaim`, `VaultStaticSecret`) is created
   by the **Go reconciler at runtime via discovery**, never templated. `Keycloak` and
   `KeycloakRealmImport` CRs are deferred to #467. This doc does not change the reconciler split
   — it only sequences the *operators that own those CRDs* ahead of the Probaitio install.

> **Why `required` is the blocker, mechanically.** OLM compiles each `required` CRD into an
> `olm.gvk.required` property on the bundle in the FBC. At `InstallPlan` creation the resolver
> must satisfy every required GVK from *installed CRDs or other bundles in reachable catalogs*.
> Our prereq operators are installed out-of-band (not from our catalog), so the only way the
> constraint is satisfiable is if their CRDs already exist. Absent them, the Subscription's
> InstallPlan goes to `Failed` / `constraints not satisfiable`. Hence section (3).

## (3) The prereq bootstrap — **the actual fix** (single-tenant MVP)

For the single-tenant MVP the required CRD set **shrinks** relative to the full #467 stack.
The Probaitio `Subscription` InstallPlan fails admission unless
`vaultstaticsecrets.secrets.hashicorp.com` already exists (and `objectbucketclaims.objectbucket.io`
if ODF/NooBaa blob storage is used). So we install + wait-Ready for **VSO** and stand up +
seed **Vault** *before* applying section 2c. RHBK/Keycloak and ODF/NooBaa-OBC bootstrap steps
are **deferred to #467** (see the deferred section below). Order matters; each step gates on a
CRD-exists or CSV-`Succeeded` check.

### 3a. Ordered runbook — MVP (decisive sequence)

1. **Cluster prereqs (out of scope to install here, documented):** OperatorHub default catalogs
   reachable for VSO (ships in `community-operators` or `certified-operators`). Etcd
   encryption-at-rest enabled if required by policy.
2. **Vault** itself (Helm chart, ns `vault`) → init/unseal → enable `kv-v2` at `probaitio/` →
   seed paths (3c) → enable Kubernetes auth + role `probaitio`. **Then** the **VSO operator**
   (`vault-secrets-operator`) → wait CSV `Succeeded` → wait
   `vaultstaticsecrets.secrets.hashicorp.com` CRD. VSO needs a reachable, seeded Vault before
   the first Probaitio reconcile (which creates a `VaultStaticSecret` that VSO immediately tries
   to sync).
3. *(Optional — if ODF/NooBaa blob substrate is used)* **ODF operator** (`odf-operator`,
   ns `openshift-storage`) → wait CSV `Succeeded` → create a **standalone MCG `StorageCluster`**
   (NooBaa only, no Ceph) → wait `ObjectBucketClaim` CRD + NooBaa `Ready`. Provides the S3
   endpoint. Skip if using PVC-based blob storage.
4. **Only now** apply `00-namespace` → `10-pullsecret` → `20-catalogsource` → wait CatalogSource
   `READY` (grpc pod healthy) → `30-operatorgroup` → `40-subscription`.
5. **Approve the InstallPlan** (Manual): find the generated `InstallPlan`, confirm it references
   `probaitio-operator.v0.1.0` and that resolution succeeded, then `approved: true`.
6. Wait Probaitio CSV `Succeeded`, then create a `DashboardInstance` CR and/or a `RemoteSession`
   CR (the alm-examples).

### 3b. `deploy/openshift/bootstrap.sh` (small, dependency-light, idempotent)

```bash
#!/usr/bin/env bash
# Ordered prereq + Probaitio installer (single-tenant MVP). Pure oc/kubectl + jsonpath waits.
set -euo pipefail
OC=${OC:-oc}
TIMEOUT=${TIMEOUT:-600s}
USE_ODF=${USE_ODF:-false}   # set to true if ODF/NooBaa blob substrate is used

wait_crd()  { echo ">> wait CRD $1"; "$OC" wait --for=condition=Established "crd/$1" --timeout="$TIMEOUT"; }
wait_csv()  { # $1=ns  $2=csv-name-prefix
  echo ">> wait CSV $2 Succeeded in $1"
  for i in $(seq 1 60); do
    phase=$("$OC" get csv -n "$1" -o jsonpath="{.items[?(@.metadata.name=~\"$2\")].status.phase}" 2>/dev/null || true)
    [ "$phase" = "Succeeded" ] && { echo "   CSV $2 Succeeded"; return 0; }
    sleep 10
  done
  echo "!! CSV $2 did not reach Succeeded"; exit 1
}
wait_catalog() { echo ">> wait CatalogSource $1 READY";
  for i in $(seq 1 30); do
    s=$("$OC" get catalogsource "$1" -n openshift-marketplace -o jsonpath='{.status.connectionState.lastObservedState}' 2>/dev/null || true)
    [ "$s" = "READY" ] && return 0; sleep 10; done; echo "!! catalog not READY"; exit 1; }

# 1. Vault + seed (see seed-vault.sh / 3c) BEFORE VSO so VSO has something to sync
helm upgrade --install vault hashicorp/vault -n vault --create-namespace -f prereqs/vault-helm-values.yaml
./seed-vault.sh                                # init/unseal, enable kv-v2, write paths, k8s auth

# 2. VSO -> VaultStaticSecret CRD (MVP required prereq)
"$OC" apply -f prereqs/vso-subscription.yaml
wait_csv vault-secrets-operator 'vault-secrets-operator'
wait_crd vaultstaticsecrets.secrets.hashicorp.com

# 3. (optional) ODF + standalone MCG -> ObjectBucketClaim CRD
if [ "$USE_ODF" = "true" ]; then
  "$OC" apply -f prereqs/odf-subscription.yaml
  wait_csv openshift-storage 'odf-operator'
  "$OC" apply -f prereqs/odf-storagecluster-mcg-standalone.yaml
  wait_crd objectbucketclaims.objectbucket.io
  "$OC" wait --for=jsonpath='{.status.phase}'=Ready noobaa/noobaa -n openshift-storage --timeout="$TIMEOUT" || true
fi

# 4. NOW the Probaitio catalog + subscription (required CRDs satisfied)
"$OC" apply -f 00-namespace.yaml -f 10-pullsecret.yaml -f 20-catalogsource.yaml
wait_catalog probaitio-catalog
"$OC" apply -f 30-operatorgroup.yaml -f 40-subscription.yaml

# 5. approve the Manual InstallPlan
ip=$("$OC" get installplan -n probaitio -o jsonpath='{.items[0].metadata.name}')
"$OC" patch installplan "$ip" -n probaitio --type merge -p '{"spec":{"approved":true}}'
wait_csv probaitio 'probaitio-operator'

echo "OK: Probaitio operator installed. Create a DashboardInstance or RemoteSession CR to proceed."
```

> `wait_csv`'s `=~` jsonpath name match is shorthand here; in the committed script use a small
> `oc get csv -o name | grep` loop (jsonpath has no regex on every oc version). The control flow
> — CRD-exists then CSV-Succeeded, per dependency, before the Probaitio CatalogSource — is the
> load-bearing part.

`deploy/openshift/prereqs/odf-storagecluster-mcg-standalone.yaml` (NooBaa-only, no Ceph — we
only need the S3 API; used only when `USE_ODF=true`):

kind: StorageCluster
metadata:
  name: ocs-storagecluster

  multiCloudGateway:

### 3c. Vault seeding (`seed-vault.sh`, summarized; full detail in `40-*` doc)

Before the **first reconcile**, the kv-v2 paths the `VaultStaticSecret` references must exist, or
VSO sync errors and the Probaitio pod's `envFrom` secret is empty (server boots without S3 creds
and fail-closes). Minimum seeds for the single-tenant MVP:

```bash
vault secrets enable -path=probaitio kv-v2
vault kv put probaitio/server \
  S3_ACCESS_KEY_ID=<from-OBC-secret-or-PVC-placeholder> \
  S3_SECRET_ACCESS_KEY=<from-OBC-secret-or-PVC-placeholder> \
  S3_ENDPOINT=https://s3.openshift-storage.svc \
  S3_BUCKET=<OBC-generated-bucket-name>
# OIDC_CLIENT_ID / OIDC_CLIENT_SECRET are deferred to #467 (Keycloak)
vault auth enable kubernetes
vault write auth/kubernetes/role/probaitio \
  bound_service_account_names=probaitio \
  bound_service_account_namespaces=probaitio \
  policies=probaitio ttl=1h
```

Chicken-and-egg note for the blob substrate: S3 keys are produced *by* the OBC, which the
**reconciler** creates. So the seed runs in two passes — placeholder seed pre-reconcile (so VSO
has a path), then the reconciler writes the real values back (or the operator reads the OBC secret
directly and the `VaultStaticSecret` is only for operator-managed extras). The `10-*`/`40-*` docs
own that handshake; this doc's contract is only: **VSO CRD + a reachable, kv-v2-enabled Vault
with the `probaitio` k8s-auth role exist before the Probaitio CSV reconciles.**

## (4) Quay publish path — extending `docker-publish.yml`

Today `.github/workflows/docker-publish.yml` builds two GHCR images (server + SPA) on push to
`master`, `v*` tags, and releases. The operator/bundle/catalog images are a **different cadence
and registry** (private Quay, released per operator semver, not on every master push), so add a
**separate workflow** rather than overloading the existing one — keeps the fast app-image path
unblocked and avoids opm/operator-sdk toolchain installs on every commit.

New `.github/workflows/operator-publish.yml`:

```yaml
name: Publish operator (OLM bundle + catalog)
on:
  push:
    tags:
      - "operator-v*"          # e.g. operator-v0.1.0 — decoupled from app v* tags
  workflow_dispatch:
    inputs:
      version: { description: "operator semver e.g. 0.1.0", required: true }
env:
  QUAY_REG: quay.io
  ORG: probaitio
permissions: { contents: read }
jobs:
  publish:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - name: Resolve VERSION
        id: v
        run: echo "version=${{ github.event.inputs.version || github.ref_name }}" | sed 's/operator-v//' >> "$GITHUB_OUTPUT"
      - name: Log in to Quay
        uses: docker/login-action@v4
        with: { registry: quay.io, username: "${{ secrets.QUAY_USERNAME }}", password: "${{ secrets.QUAY_TOKEN }}" }
      - name: Install operator-sdk + opm
        run: |
          curl -sSLo /usr/local/bin/operator-sdk https://github.com/operator-framework/operator-sdk/releases/latest/download/operator-sdk_linux_amd64
          curl -sSLo /usr/local/bin/opm          https://github.com/operator-framework/operator-registry/releases/latest/download/linux-amd64-opm
          chmod +x /usr/local/bin/operator-sdk /usr/local/bin/opm
      - name: Build + push operator image
        run: |
          V=${{ steps.v.outputs.version }}
          docker build -t $QUAY_REG/$ORG/probaitio-operator:v$V operator
          docker push   $QUAY_REG/$ORG/probaitio-operator:v$V
      - name: Regenerate + validate + push bundle
        working-directory: operator
        run: |
          V=${{ steps.v.outputs.version }}
          make bundle VERSION=$V IMG=$QUAY_REG/$ORG/probaitio-operator:v$V
          operator-sdk bundle validate ./bundle --select-optional suite=operatorframework
          docker build -t $QUAY_REG/$ORG/probaitio-operator-bundle:v$V -f bundle.Dockerfile .
          docker push   $QUAY_REG/$ORG/probaitio-operator-bundle:v$V
      - name: Render + validate + push catalog (FBC)
        working-directory: operator
        run: |
          V=${{ steps.v.outputs.version }}
          opm render $QUAY_REG/$ORG/probaitio-operator-bundle:v$V --output=yaml > catalog/probaitio/_bundle.yaml
          opm validate catalog
          opm generate dockerfile catalog
          docker build -t $QUAY_REG/$ORG/probaitio-catalog:v$V -f catalog.Dockerfile .
          docker push   $QUAY_REG/$ORG/probaitio-catalog:v$V
```

Notes:
- New secrets: `QUAY_USERNAME`, `QUAY_TOKEN` (robot account scoped to the three repos).
- The catalog step re-renders the bundle into the committed FBC and `opm validate`s; the channel
  `entries` block stays hand-authored in `catalog/probaitio/catalog.yaml` (don't let the
  workflow clobber upgrade edges — render into a separate `_bundle.yaml` or assemble in a script).
- Keep this **out of** `docker-publish.yml` so the app-image publish (which gates deploys) never
  waits on opm/operator-sdk downloads, and a malformed bundle can't block a server hotfix.
- **CI runtime-boot gate** (locked review decision, lives in this area): a separate job/workflow
  must boot the actual server runtime image and `curl /healthz` — that gate is independent of OLM
  packaging but is the safety net proving the dependency-free server still boots; cross-referenced
  from the `20-*` server doc, not duplicated here.

### Deferred: RHBK/Keycloak prereq bootstrap

> (RHBK 24.x = `v2alpha1`, newer = `v2beta1`) and keep this field in lockstep with the bootstrap.
> The **reconciler** resolves the live GVK at runtime via discovery and requeues behind a
> CRD-exists check (see `10-*` doc) — that is the real correctness mechanism; the CSV field is

### Deferred: encrypted-blob store, public write gate, API-key compute proxy

The following are #467 multi-tenant, zero-knowledge-at-rest features — **not MVP**:

- **Client-side encryption**: the sidecar holds the per-tenant key and encrypts artifact blobs
  before push; the server sees only ciphertext. The `artifact-source` interface (ADR 0011 §1)
  is designed so adding this is an encryption step at the boundary, not a re-architecture.
- **Encrypted-blob / ciphertext store**: the blob substrate stores ciphertext; the server cannot
  decrypt without the tenant key. Etcd encryption-at-rest (cluster-level) covers metadata;
  blob encryption covers contents.
- **Public same-origin / CSRF write gate**: the invite-only public write path with
  CSRF-token protection for the multi-tenant intake endpoint.
- **API-key compute proxy**: the operator-pay compute intermediary (LiteLLM/agentgateway
  behind an API-key facade) for multi-tenant dispatched sessions.

The `artifact-source` + push-ingest substrate (#1248) is **designed for** this layer (opaque
blobs, signature-keyed, no parsed-SQL store), so #467 attaches without re-architecture.

### Deferred: ODF/NooBaa-OBC as mandatory prereq

For the MVP the blob substrate may be a PVC; ODF/NooBaa-OBC is optional (controlled by
`USE_ODF=true` in `bootstrap.sh`). In the #467 multi-tenant deployment ODF/NooBaa-OBC becomes
a mandatory prereq because the encrypted-blob store requires a true S3 endpoint with per-tenant
bucket isolation. At that point promote the ODF bootstrap step from optional to required and
uncomment the `ObjectBucketClaim` entry in the CSV `required` block.
