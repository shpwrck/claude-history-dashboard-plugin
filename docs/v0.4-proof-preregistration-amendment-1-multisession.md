## 0. Why this amendment exists

The v0.4 batch returned a **credible but uninformative NULL** (external review
#1078): every fixture in `fixtures/proof/repo-map-context-waste/` runs as a
single isolated session, but the #890 treatment ("reference stable files instead
of re-reading them **each session**") targets *cross-session* re-read waste. In
a single session a file is read once and then served from cache, so the
mechanism can remove at most one first read — it is **structurally near-unable to
exhibit the effect** (corroborated by `observedUsdPerMo = 0`). The v0.4 NULL is
therefore a NULL *about single-session scope*, not about the treatment.

This amendment corrects the **design**, not the thresholds. It introduces a
multi-session fixture structure where the agent legitimately works across several
cold sessions over the same stable files, so the treatment can remove re-paid
cold-read tokens. The parent pre-registration's hypothesis, metrics, decision
rule, and N are carried forward **unchanged** (§ 3 below); only the corpus
structure and the injection vehicle change.

**The v0.4 NULL stays on record.** It is superseded *by design correction*, not
overturned. It remains valid and true for single-session scope; this amendment
tests the multi-session scope the detector actually claims. The proof receipt
links v0.4 (NULL, single-session) → v2 (this amendment, multi-session).

## 1. What changes (structure only)

1. **Multi-session chains.** Each matched pair becomes an ordered chain of
   **M = 8 sessions** per arm, run sequentially over ONE accumulating fixture
   tree. Each session is its own COLD jailed worker (a fresh conversation), so
   the control arm re-reads the stable file from cold each session while the
   treatment arm does not need to. M = 8 is fixed here from a workflow rationale
   — *a feature evolved over roughly a work-week of sessions against a stable
   module* — and is explicitly **NOT** tuned to the MDE.

2. **Treatment vehicle = persistent `CLAUDE.md`.** The #890 recommendation is
   materialized as a `CLAUDE.md` in the treatment tree, present in *every*
   session's project context — exactly how the real fix is deployed — instead of
   the v0.4 one-shot prompt prepend. The control tree has no such file. This is a
   structural refinement of the §2 injection mechanism, not a change of
   treatment: the injected text is still the #890 fix snippet verbatim (same
   `## Stable reference files` heading + `- @<path> — <symbols>` markers, so the
   #583 eligibility screen still recognizes it as that finding). Both arms run
   the IDENTICAL 8-task chain; the ONLY difference is the presence of this file.

3. **Cost metric = chain-total.** The §4 primary metric (total task cost in
   tokens → dollars) is computed as the **sum across the M sessions** of a chain.
   The §5 paired-median test, Wilcoxon, and bootstrap CI are applied to the
   per-fixture **chain** deltas exactly as the parent doc specifies for per-task
   deltas — same statistics, the unit of analysis is now the chain.

4. **Dose-response (SUPPORTING readout only).** The batch additionally records
   the cumulative cost delta at each session boundary (sessions 1..8), median
   over DECIDED pairs, to characterize the *onset* of the cross-session effect.
   This curve is descriptive. **It never sets the verdict** and may not be used
   to select a session count at which the result is significant — see § 4.

## 2. Anti-gaming constraints (pre-registered, binding on every fixture)

To prevent the fixtures from being (even unconsciously) tilted toward an
observable effect — the integrity risk that kept #1603 human-in-the-loop — every
chain fixture MUST satisfy all six:

1. **Identical-except-the-reference.** Both arms share the same tree and the same
   M-task chain. The only difference is presence/absence of the treatment
   `CLAUDE.md`.
2. **Treatment carries only what #890 emits** — a stable-file reference + symbol
   list — never a solution hint. Treatment may finish *cheaper*, never *more
   correctly*.
3. **No coercion of behavior.** No instruction tells control to re-read or
   treatment not to read. The re-read (control) and citation-instead-of-read
   (treatment) must emerge from priming, not be scripted.
4. **Realistic stable files.** The stable file is a genuine module the tasks need
   symbols from, at realistic size — never bloated to inflate per-read tokens.
5. **No content leakage.** Task instructions must not quote the stable file's
   contents or symbols; the symbols live only in the file (control) or the
   reference (treatment).
6. **Solvable-with-symbols, needs-the-file.** Each task must be genuinely
   solvable *given the symbols* (so the reference truly substitutes for a read)
   and genuinely *require* the stable file (so control naturally re-reads). A
   task needing neither is dropped.

Self-correcting property (kept on record): if a *control* agent guesses symbols
without reading, it either fails Gate 0 (excluded) or also saves tokens — both of
which *shrink* the measured delta. That failure mode therefore biases **against**
H1, the safe direction.

## 3. What is CARRIED FORWARD UNCHANGED from the parent pre-registration

No threshold below moves; reproduced here only to make the freeze explicit.

- **Hypothesis H1 / H0** — unchanged (§ 1 of the parent doc).
- **MDE** — ≥ 15% median per-chain cost reduction.
- **PROVEN / NULL / REFUTED decision rule** — § 5 of the parent doc, verbatim,
  applied to per-chain deltas: paired-median reduction ≥ 15% AND bootstrap 95% CI
  entirely below zero AND Wilcoxon one-sided p < 0.05 AND quality-hold passes AND
  N ≥ 12 DECIDED chain-pairs.
- **Quality hold (Class B rider)** — treatment DECIDED-success rate within 5pp of
  control's.
- **N = 12** DECIDED chain-pairs; **k = 3** runs per arm (each run an 8-session
  chain). Exclusion accounting and the "engineering not-yet-provable" branch
  (§ 6) carry forward unchanged.
- **Gate 0** — the fixture's objective gate, run on the FINAL accumulated tree
  after all M sessions: build/tests/acceptance as before.
- **Judge** — tiebreaker only (§ 4 parent), unchanged.

## 4. Single primary test (no M-shopping)

The primary PROVEN/NULL/REFUTED verdict is evaluated **once**, on the
**chain-total cost at the full M = 8**. The per-session dose-response curve (§ 1.4)
is supporting only and may not be searched for a significant session count. This
keeps exactly one pre-registered comparison and forecloses multiple-comparisons
p-hacking across session boundaries.

## 5. Corpus construction

- **Reuse-and-convert.** The existing 12 pairs are converted in place: each keeps
  its tree foundation, stable file, and `wasteReason` taxonomy, and replaces its
  single task with an ordered 8-task chain over the same stable file.
- **Per-fixture escape hatch.** If a given tree genuinely cannot carry a
  believable 8-task chain, that ONE fixture is replaced rather than contrived;
  any such replacement is listed here before sign-off.
- **Solvability is verified, not assumed.** For each chain, a reference solution
  implementing all 8 tasks using only the stable file's symbols is confirmed to
  pass Gate 0, and the shipped (initial) tree is confirmed to FAIL Gate 0 — so
  every fixture is a real, solvable task. Reference solutions are not committed.
- **Fixtures frozen before the batch.** As in the parent doc, no chain is added
  or dropped after the first run.
- Escape-hatch conversions applied: the two `diff`-gate pairs
  (`high-centrality-rename-diff`, `config-backed-flag-rename-diff`) were
  converted to `test`-gate chains. A `diff` gate ships an `expected/` answer key
  in the tree, which would let an agent solve the task by reading the answer
  instead of re-reading the stable file — defeating the cross-session re-read
  premise for those pairs. Their stable file, `wasteReason`, and pair id are
  unchanged; only the gate kind/command and the consumer tasks changed. No pair
  was dropped; N stays 12.

## 6. Run governance (the #2083 run, NOT this prep issue)

This amendment governs the apparatus + corpus only. The run itself (#2083) is
human-gated and budgeted; recorded here so the credibility chain is complete:

- **Model:** Opus 4.8 primary (the receipt's verdict is conditional on it).
  Sonnet/others are § 7 revalidation targets, not the primary.
- **Calibrate before committing the cap.** A 16-session calibration slice
  (1 chain-pair × 2 arms × k=1 × M=8, hard-capped ~$10) measures real $/session
  and smoke-tests the loop; the maintainer authorizes the full-batch total cap
  from that measurement.
- **Two hard human gates:** (1) maintainer signs off THIS amendment (its commit
  predates any run); (2) maintainer authorizes the full-batch cap from the
  calibration number.
- **Jail mandatory + killswitch + human-trigger-only.** The run never fires from
  the autonomous loop or a schedule.
